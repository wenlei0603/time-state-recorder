Time State Recorder v1.2 PRD

工作洞察与视觉摘要

把技术事件流翻译成人能复盘的工作叙事。

    01 / Product Intent

    从“记录窗口切换”变成“理解一天在做什么”

    原始事件继续保留，但默认呈现改成 3 分钟活动桶、项目分类、注意力状态和视觉摘要。

    产品要回答的问题

    • 我今天主要推进了哪些项目？
    • 哪些时间是稳定专注，哪些时间被切碎？
    • 浏览器里到底是在查资料、写代码，还是分心？
    • 有什么截图证据支持这些结论？
    本地优先 证据可追溯 默认 3 分钟 长期统计
    02 / Current Problem

    现在的 Timeline 太像日志，不像复盘工具

    每次窗口切换都展示出来，对调试有用，对理解自己一天的工作状态不够友好。

    事件太碎

    浏览器、微信、Word 来回切换会产生很多短事件，人需要自己拼出上下文。

    缺少语义

    系统知道你在 Chrome，但不知道这是查资料、写 PRD、看视频，还是临时分心。

    截图未被理解

    缩略图可以看，但没有被转成可搜索、可统计、可归类的文字摘要。

    目标：把碎事件压缩成可读叙事

    09:12
    写代码
    10:03
    查资料
    10:18
    沟通
    03 / Data Flow

    核心链路：原始事件到人类洞察

    不要降低采集精度。先保留原始事件，再在查询层聚合，这样未来可以重新解释历史数据。

    窗口事件 每秒采样，窗口身份变化时写入。
    3 分钟桶 把碎事件聚合成固定时间片。
    分类层 项目、活动类型、注意力状态。
    视觉摘要 每 5 分钟截图，模型写摘要。
    洞察视图 聚焦块、切换率、长期趋势。

    关键原则：采集保持细，展示变粗，解释变人类。

    05 / Category Model

    不要只有一个标签，要分成三个维度

    “项目是什么”、“活动类型是什么”、“注意力状态怎样”是三个问题，混在一起会导致长期统计不可用。

    Project

    回答：这段时间属于哪个项目？

    PhD Paper TSR Teaching Unknown

    Activity

    回答：这是什么类型的活动？

    Research Coding Communication Loafing

    Attention

    回答：这段时间是否被切碎？

    Deep Focus Steady Light Switching Fragmented
    06 / Loafing & Rules

    Loafing 不应由系统武断判断

    默认应该是可解释、可修正、可由用户定义的分类。否则系统会变成监控工具，而不是自我洞察工具。

    第一版推荐逻辑

    • 用户规则明确命中，才标为 loafing。
    • 模型可以给出候选，但需要低置信度或等待确认。
    • 同一个网站可能既是研究，也可能是分心，要看项目和截图上下文。

    更适合统计的表达

    • Non-work browsing
    • Personal
    • Unknown
    • User-confirmed loafing
    07 / Switching Insight

    切换频率是洞察，不是责备

    3 分钟桶里的 switchCount 可以转成注意力状态，帮助发现什么时候被打断、什么时候进入稳定节奏。

    Deep Focus

    切换少于等于 1 次，主活动占比 85% 以上。

    Steady

    切换少于等于 2 次，主活动占比 65% 以上。

    Light Switching

    有切换，但仍能看出主线任务。

    Fragmented

    切换很多，没有清晰主活动，适合回看原因。

    09 / Visual Summary

    每 5 分钟高分辨率截图，让视觉模型写摘要

    缩略图用于快速定位，高分辨率截图用于模型理解上下文。默认仍然保护隐私。

    5 分钟截图保留可读文字和窗口结构。
    Blocker 过滤敏感窗口不保存、不分析。
    模型摘要描述工作上下文、项目线索、风险。
    证据入库可搜索、可统计、可回看。

    摘要不是 OCR 全文

    默认只写“正在编辑 Rust API 和测试”，不复制私密正文。Raw 模式和本地模型可以放宽。

    11 / Long-Term Analytics

    这套结构的价值在长期统计

    只看当天是复盘。跨天、跨周、跨项目分析，才会形成真正的自我洞察。

    项目时间

    按天、周、月看每个项目投入，减少主观估计。

    深度专注

    统计 deep focus 小时数，以及它出现在哪些项目和时间段。

    碎片化趋势

    看切换率如何变化，找出最容易被打断的时段。

    沟通负载

    观察 WeChat、邮件、会议占比是否挤压项目工作。

    浏览器主题

    用标题和视觉摘要聚类浏览器活动。

    Loafing 趋势

    只统计用户确认或规则明确的非工作活动。

    12 / Technical Architecture

    技术架构要把采集、派生、分析、呈现分开

    软件工程上的核心原则：原始证据不可丢，派生结果可重算，模型能力可替换，隐私策略在边界统一执行。

    Capture Layer只采集事实：窗口、输入、生命周期、缩略图、高分辨率截图。不判断项目或 loafing。
    Raw Evidence StoreSQLite 和图片文件保存不可变证据，负责 session、时间、文件路径和外键关系。
    Derivation Engine纯函数优先：TimeEvent、3 分钟 bucket、浏览器标题归一化、Focus Block、switching metrics。
    Insight Engine把 bucket 解释成项目、活动类型、注意力状态和日级总结，可结合规则、人工修正、视觉摘要。
    Visual Pipeline高分截图经过 blocker 后入队，模型 provider 异步分析，失败不影响主采集。
    Local API + UIAPI 返回稳定 DTO，前端 Activity Review 展示洞察，原始事件作为可展开证据。
    13 / Data Lifecycle

    数据生命周期：先保存事实，再生成解释

    不要让模型输出成为唯一真相。所有洞察都应该能从原始证据和规则重新生成。

    1. 采集window focus、input、lifecycle、screenshots。
    2. 入库SQLite 存 metadata，图片存文件系统。
    3. 派生构造 intervals、3 分钟桶、切换次数。
    4. 丰富项目规则、活动分类、注意力状态、视觉摘要。
    5. 呈现Focus Blocks、分类卡、切换洞察、长期统计。

    可重算

    修改分类规则后，可以重新生成历史 bucket 和 summary。

    可审计

    每个洞察都能展开到窗口标题、截图摘要、原始事件证据。

    可降级

    视觉模型不可用时，窗口/输入/截图 metadata 仍然能支撑基础洞察。

    新增能力应按端口和适配器组织：领域模型和派生逻辑可测试，数据库和模型供应商只是适配器。

    最佳实践要求

    • DB row、domain model、API DTO 分开。
    • 新增表必须有 schema migration。
    • 视觉模型通过 provider interface 调用。
    • HTTP route 不直接写模型供应商代码。
    • bucket/category/focus block 用纯函数单测覆盖。
    • 隐私策略在采集、分析、返回三个边界执行。
    15 / Build Order

    MVP 应该分阶段做，不要一次吞掉全部

    先把 3 分钟活动桶和 Activity Review 做稳，再接入高分辨率截图和视觉模型。

    1. 后端桶/api/activity-buckets，默认 180 秒。
    2. 洞察前端分类卡、Focus Blocks、切换洞察。
    3. 高分截图5 分钟一张，配置开关保护隐私。
    4. 模型接口provider abstraction，不绑定厂商。
    5. 单张分析先手动分析，再做批量队列。

    一句话记忆

    原始数据是证据，3 分钟桶是语义，视觉摘要是解释，长期统计是价值。
